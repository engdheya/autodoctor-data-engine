## 1. تحليل قاعدة البيانات الفعلية

### 1.1 الشكل العام

- SQLite 3 (قُرئت بـ 3.40.1)، صفحة 4096 بايت، `journal_mode = delete`.
- **22 جدولًا + 13 View** جاهزة للعميل: `v_dtc_search`, `v_dtc_lookup`, `v_dtc_summary`,
  `v_dtc_causes`, `v_dtc_symptoms`, `v_dtc_repairs`, `v_dtc_tests`, `v_dtc_related`,
  `v_dtc_provenance`, `v_dtc_conflicts`, `v_manufacturers`, `v_pids`, `v_vehicles`.
- المخطط مُصدَّر في `db/schema.sql`، والتوثيق في `docs/DATABASE_SCHEMA.md` و`docs/DATA_DICTIONARY.md`.

### 1.2 بنية الهوية — أهم نقطة معمارية

`dtc_codes` لا يمثّل «الكود»، بل يمثّل **سياقًا** للكود:

```
context_key = "P0301|sae_j2012|generic:generic"
context_key = "P0301|manufacturer_specific|manufacturer:audi"
context_type ∈ {generic, manufacturer, ecu, vehicle_variant}
```

- **940** كودًا لها أكثر من سياق، وأقصى عدد سياقات لكود واحد **22**.
- لذلك: أي واجهة تعرض «P0301» بمعنى واحد تكون **خاطئة** عندما توجد سياقات متعددة.
  التطبيق سيعرض تبويب سياقات (Generic + الشركات) ويشرح الفرق، ولا يختار معنى تلقائيًا.
- `context_key` UNIQUE وهو **مفتاح الربط** الصحيح في كل الاستعلامات، لا `code`.

### 1.5 قياس أداء البحث على الملف الحقيقي (تم هنا، لا تقديرًا)

| الاستعلام | الزمن (سطح مكتب) | الخطة |
| --- | --- | --- |
| `dtc_codes WHERE code = ?` | 0.08 ms | فهرس `idx_dtc_codes_code` |
| `dtc_codes WHERE code LIKE 'P030%'` | 1.20 ms | covering index |
| `v_dtc_search WHERE code_compact = ?` | 11.52 ms | **SCAN** (الـView يمنع استخدام الفهرس) |
| بحث مرتّب (كود + عنوان) limit 25 | 2.7–9.7 ms | مسح محدود |
| مسح كامل على الوصف (`LIKE '%circuit%'`) | 10.4 ms | مسح كامل |
| FTS5 (بناء + استعلام) | بناء 145 ms / استعلام 0.18 ms / +8.9 MB | اختياري |

**الاستنتاج:** لا نحتاج FTS5 في الإصدار الأول. البحث بـ LIKE + فهارس، مع تأخير 120 ms
(debounce) وتنفيذ في Isolate، يعطي 15–40 ms على جهاز متوسط — مقبول تمامًا. سنفتح
`dtc_codes` مباشرة في البحث الحرفي بدل `v_dtc_search` لتفادي المسح الكامل.

**تحذير فني مهم:** `v_dtc_search` تحتوي استعلامات فرعية مترابطة لكل صف؛ استخدامها في
قائمة من 10,000 صف يعني 10,000 مسح. لذلك: القوائم تستخدم استعلامات مركّبة مخصّصة، والـView
يبقى للتفاصيل فقط.

## 2. التصور المعماري

Clean Architecture بطبقات مفصولة، وحالة واحدة (Riverpod) ومصدر بيانات واحد للقراءة:

```
lib/
  core/            constants · errors(AppFailure) · l10n · routing · theme · utils · widgets
  domain/          entities(DtcCode, DtcDefinition, Cause, Symptom, RepairEstimate, Vehicle, DiagnosisRecord)
                   repositories (abstract)  ·  usecases (SearchCodes, GetDtcDetail, SaveVehicle, …)
  data/            database/ (AppDb opener, read-only ref DB, user DB, migrations, sha256)
                   datasources/ (RefLocalDataSource: SQL only here)
                   models/ (row → entity mappers)
                   repositories/ (implementations)
  features/        splash · onboarding · home · search · dtc_details · inspection
                   garage · history · favorites · reports · settings
  services/        obd/ (abstract transport + future ELM327) · ai/ (assistant interface) · report/ (PDF)
  main.dart
```

قواعد ملزمة في الكود:

1. **لا SQL خارج `data/database` و`data/datasources`.** الشاشات تستدعي UseCase فقط.
2. **قاعدة المرجع تُفتح للقراءة فقط** (`OpenDatabaseOptions(readOnly: true)`)، ولا تُعدَّل
   أبدًا؛ كل بيانات المستخدم في ملف ثانٍ `autodoctor_user.db`.
3. **لا بيانات وهمية في أي طبقة.** كل حقل غير موجود في القاعدة = `null`، والواجهة تُخفي
   القسم أو تعرض «غير متوفر في المصدر».
4. **كل معلومة معها مصدرها**: `provenance_summary` + `dtc_evidence_sources` +
   `dtc_definitions.verification_status` تظهر شارة على كل بطاقة.
5. **السياق أولًا**: أي شاشة تفاصيل تعمل على `context_key`، وتُظهر محدّد سياق عند تعددها.

### 2.1 مسار البيانات (Read path)

```
Widget ← Riverpod Provider ← UseCase ← Repository ← RefLocalDataSource ← Ref DB (read-only)
                                           ↖ UserRepository ← User DB (read-write, separate file)
```

### 2.2 مسار التوسّع المستقبلي

- `services/obd/` يعرّف `ObdTransport` (connect/readDtcs/liveData/freezeFrame/clearDtcs) —
  **واجهة فقط**، بلا تنفيذ ولا أوامر مسح في الإصدار الأول.
- `services/ai/` يعرّف `DiagnosisAssistant` يأخذ `DtcDetail` من القاعدة فقط، ويجب أن يُعيد
  `answeredFrom: database | inference` مع كل جواب. لا يُنفَّذ أي مزوّد/اشتراك مدفوع.

## 4. خطة ربط Flutter مع SQLite

1. **التضمين**: القاعدة تُوضع في `assets/db/autodoctor-0.9.0-public.sqlite` مع
   `android { aaptOptions { noCompress 'sqlite' } }`؛ بدونها يضغط AAPT الملف ويفشل الفتح.
2. **النسخ الأول**: عند أول تشغيل تُنسخ إلى `getDatabasesPath()` إن لم تكن موجودة
   (نسخ على 64 KB دفعة، في Isolate) ثم تُفتح `readOnly: true`.
3. **التحقق**: SHA‑256 المحسوب يُقارن بقيمة مضمنة في `assets/db/db_manifest.json`
   (نفس `sha256` في `data/reports/app-db-analysis.json`)؛ أي اختلاف ⇒ شاشة خطأ صريحة،
   لا فتح صامت لملف تالف.
4. **قاعدة المستخدم**: `autodoctor_user.db` منفصلة (`vehicles`, `diagnosis_records`,
   `favorite_codes`, `notes`) مع `PRAGMA user_version` وترحيلات متسلسلة في `migrations/`.
5. **التحديث**: عند وصول إصدار قاعدة جديد يُنزَّل الملف (لاحقًا) ويُستبدل كملف مرجعي كامل
   بعد التحقق من SHA؛ لا تُعدَّل القاعدة المرجعية في مكانها.
6. **الاستعلامات**: `context_key` مفتاح كل شيء؛ قوائم البحث تستعلم `dtc_codes` +
   `dtc_definitions` مباشرة (لا الـViews في القوائم)؛ التفاصيل تستخدم `v_dtc_*`.
7. **الأداء**: كل بحث في Isolate مستقل (`sqflite_common_ffi` غير مطلوب على الجهاز)،
   `LIMIT` + `OFFSET` للصفحات، وفتح اتصال واحد مشترك للقراءة.
8. **العربية/RTL**: `flutter_localizations` + `intl`، `Directionality` من `Localizations`,
   وتنسيق الأرقام بـ `NumberFormat` لكل لغة.

## 7. المخاطر والقرارات المطلوبة منك

### مخاطر تقنية (بترتيب الأثر)

1. **لا يوجد Flutter SDK في بيئتي** ⇒ لا APK من هنا. الحل: سير عمل GitHub Actions يبني
   APK ويُرفعه كـ artifact (يحتاج صلاحية `workflow` في التوكن)، أو تبني على جهازك.
2. **57 MB أصل داخل APK** ⇒ APK ≈ 62–70 MB. مقبول، لكن يمنع نشره على بعض المتاجر؛ الحل
   لاحقًا: تنزيل القاعدة عند أول تشغيل.
3. **`v_dtc_search` بطيئة في القوائم** ⇒ قرار معماري: لا نستخدمها للقوائم (مُقاس أعلاه).
